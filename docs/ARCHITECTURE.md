# 架构（v2，2026-10-22 起）

## 为什么重写

旧实现是 AstrBot 插件：`main.py` 4600 行里混着门控、提示词、工具、玩法，
而且进程内存 779MB 里 97% 是 AstrBot 框架。新的核心自己实现协议与管线，
代码量小、启动快、内存低，插件化后每个能力可以独立发版。

## 分层

```
┌──────────── core（本仓库）────────────┐
│ onebot/   反向 WS + 事件模型 + action │
│ pipeline/ 门控阶段（每段一个函数）      │
│ llm/      chat / chat_tools           │
│ plugin/   插件宿主（JSON-RPC）         │
└───────────────┬───────────────────────┘
                │ unix socket + JSON-RPC（进程边界 = 语言自由）
   ┌────────────┼─────────────┬──────────────┐
persona       turtle_soup   websearch    （任意语言）
```

## 关键决策

1. **QQ 接入只做 OneBot v11**：SnowLuma 反向 WS，一个连接足够单账号。
2. **插件走进程边界**：不是 in-process import。理由：插件是"慢调用"（LLM 判题/搜索/生图，
   几百毫秒到几十秒），IPC 的亚毫秒开销可忽略；换来的是崩溃隔离、独立发版、任意语言。
   参考现有 `qqbot-asr.service`（unix socket + JSON 行）已经验证过这套模式。
3. **核心不实现玩法**：海龟汤、人格卡内容、表情库都是插件。
4. **核心默认人格只有 4 行**：没装人格插件也能说话，只是没个性。

## 里程碑

M0 收事件（已完成）→ M1 能回消息 → M2 管线骨架 → M3 LLM+工具 → M4 插件协议 → M5 真机切换

## 落地后的最终形态（2026-10-22，M5 已上线）

```
            ┌─────────── core（协议无关的内核）───────────┐
            │ runtime：收 → 管线 → 上下文装配 → 工具循环   │
            │ pipeline：白名单/频率/决定/连发合并           │
            │ context：ContextBundle（人格/规则/记忆/场景） │
            │ memory：self（她是谁）+ scope（这一处）+ recent│
            │ llm：OpenAI 兼容 chat / chat_tools           │
            │ plugin：stdio JSON-RPC 插件宿主              │
            └──────────────┬──────────────────────────────┘
                           │  Channel 协议（进程内）
        ┌──────────────────┴───────────────────┐
   adapters/cli（命令行）            adapters/onebot（SnowLuma 等）
                           │  JSON-RPC（进程外，任意语言）
        ┌──────────────────┴───────────────────┐
   plugins/personas  plugins/memory  plugins/turtle …
```

三条关键决策（都踩过坑）：

1. **事件处理不能 await 在读循环里**——否则处理函数里的 `send_group_msg` 等回包会死锁
   （消息发出去了、回包读不到、30 秒超时后模型重发，表现为"一条消息回两遍"）。
2. **渲染顺序固定**：人格+规则 → self 记忆 → scope 记忆 → 场景 → 最近 → 当前。
   实测前缀缓存命中 71~83%。
3. **记忆分三层**：self 极少写（只有主人明确要求或每日自省），scope 由后台任务写，
   recent 自动写。混在一起会被某个群的闲聊污染。
