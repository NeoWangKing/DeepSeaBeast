# 接入一个新通道（检查清单）

> 原则：**先把"这个平台到底支持什么"摸清楚、落到文档里，再动手写 adapter。**
> 否则很容易在 adapter 里自己造一层"通用抽象"去兼容想象中的差异——那是多余的一层，
> 而且以后每加一个平台都要维护它。

以 SnowLuma（QQ）为例，成品是 `docs/SNOWLUMA_API.md`：158 个动作名，分类 + 状态 + 风险。

## 第 0 步：摸清接口（**先做这个**）

把平台/协议支持的所有动作、事件、字段列出来。怎么拿：

| 平台形态 | 拿法 |
|---|---|
| 打包好的 JS/二进制（如 SnowLuma） | 从 bundle 里提取动作名字符串（见 `deploy/tools/dump-snowluma-actions.sh`） |
| 有官方协议文档（如 OneBot v11） | 照文档整理，但**以实际实现为准**（我们踩过：文档有、实现没有） |
| 有 SDK / OpenAPI | 直接导出接口清单 |

产出：`docs/<通道名>_API.md`，每个接口至少标三样：

```
动作名 | 状态（已用/未验证/未用） | 用途 | 风险（高=会改账号或群里状态）
```

**为什么值得花这一步**：SnowLuma 那份清单直接告诉我们
"表情包走 `send_custom_face` 而不是 `face` 段"、"看图用 `get_image`"、
"成员档案可以 `get_group_member_list` 一次拉全"——这些如果不先查，
就会像我们之前那样自己造一套错的抽象。

## 第 1 步：分类，别急着实现

把接口按**我们需要的三种角色**归类：

| 角色 | 含义 | 落到哪 |
|---|---|---|
| **transport** | 把消息送出去（发文本/图片/文件/表情/@） | 映射成本文的**封闭动词表** |
| **query** | 读数据（群信息、成员列表、历史消息、图片文件） | 做成工具或适配器内部调用 |
| **control / 管理** | 改变账号或群的状态（踢人、禁言、退群、改资料） | **默认不做**；要做必须先有权限模型 |

## 第 2 步：映射到封闭动词表

核心只认这几个动词（`core/capability.py`）：

```
text / at / quote / image / file / face / poke / voice
```

平台能做哪些，就在 adapter 的 `abilities` 里声明哪些；做不了的**不要声明**，
核心会自动把依赖它的工具隐藏起来（"诚实失败"原则）。

**不要**为了"兼容"而在 adapter 里发明新动词——需要新动词就是改核心，要评审。

## 第 2.5 步：行内占位符（核心协议，别自己发明）

文字里夹"平台自带表情"这件事，用的是**核心定义的占位符**（`core/capability.py`）：

```python
face_token("坏笑")     # → "[表情:坏笑]"
FACE_TOKEN_RE          # 解析用
```

- 核心负责**生成和教模型**这个写法；
- adapter 负责**翻译**：QQ → `face` 段；没有表情能力的通道不会看到它（工具不出现）；
- **adapter 不许自己拼这个字符串**——`tests/selfcheck_layering.py` 会拦。

同理，以后要加"行内贴图/行内链接"之类的新占位符，也先加在 `core/capability.py`，
再让 adapter 翻译。

## 第 3 步：实现 Channel 的四个声明

```python
class MyChannel:
    name = "myim"                 # 唯一名字
    supports = {"group", "private"}   # 负责哪类会话
    abilities = {"text", "image"}     # 能送什么（封闭动词表里的）

    def describe(self, chat) -> str:      # "这是哪儿"（人话）
    def scope_info(self, chat) -> dict:   # kind/id/key/label/name（记忆分区用，名字来自平台）
    def profile(self) -> dict:            # 平台习惯 + 行内可用物（表情清单等）
    async def start(self, on_message):    # 收
    async def send(self, out) -> SendResult:   # 发
```

`send()` 要返回 `SendResult(ok, error, confirmed)`：**`confirmed` 说的是结论确定不确定**。

| ok | confirmed | 含义 |
|---|---|---|
| True | True | 真的确认到了（回读/回执核对通过） |
| True | False | 接口收下了但没法确认（无回执）——**重试可能重复** |
| False | True | 明确失败，可以放心重试 |

通道自己决定怎么核对（QQ 用 `get_msg` 回读，微信类回读数据库）；**核心不需要知道细节**。

四条铁律：

1. **名字只能来自平台**（事件/接口），代码里不许写死任何群号、昵称、用户 id
2. **不让 adapter 做业务**：不决定回不回、不管人格、不碰记忆——它只翻译
3. **事件处理不能阻塞读循环**（我们踩过：`send_group_msg` 等回包会死锁）
4. **能力先标 `experimental`**，真机验证过一次再升 `ready`，否则不许出现在能力清单里

## 第 4 步：验证清单

- [ ] `python -m core --channel <名字>` 能起来
- [ ] 假客户端（或本机工具）能走通"收事件 → 送回包"
- [ ] 断线重连、发送超时、异常回包都有日志，不静默
- [ ] 能力矩阵启动时打印正确（`通道能力矩阵`）
- [ ] 真机验证一次真实收发（文字 + 每种声明过的动词各一次）
- [ ] 把验证结果写回 `docs/<通道名>_API.md` 的"状态"列

## 反例（我们踩过的坑）

| 坑 | 后果 |
|---|---|
| 没先摸清接口就写 adapter | 造了一套错的"通用消息段"，后来发现平台根本不是那个形状 |
| 把"能发图片"当成"会画图" | 她在群里承诺画图，其实做不到 |
| 事件在读循环里 await | 发送等回包死锁，30 秒超时后重复发消息 |
| 代码里写死测试群号/昵称 | 换个部署就废，还把隐私带进仓库 |
| 没验证就标 ready | 工具出现在能力清单里，她照着承诺，用户一测全是假的 |
