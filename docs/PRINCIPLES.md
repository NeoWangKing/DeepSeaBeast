# 设计原则

这个项目的目标只有一句话：

> **让核心像一个"人"那样和人沟通。QQ、终端、以后任何聊天软件，都只是她用来与人交流的工具。**

所以每一层只做一件事，边界不能混：

| 层 | 只负责 | 不能知道 |
|---|---|---|
| `core/` | 像人一样说话：节奏、分寸、记忆、工具、决策 | 任何具体聊天软件（QQ/微信/终端） |
| `adapters/` | 把某个软件的消息翻译成 `InboundMessage`，把 `OutboundMessage` 发出去 | 人格、记忆、提示词、玩法 |
| `plugins/` | 某种能力（人格卡、记忆、表情包、玩法） | 别的插件、核心内部 |

## 一、核心与通道分离

- 核心只认 `Channel` 抽象：要消息、要发消息、问能力（`abilities`）、问"这是哪儿"（`describe`）
- **核心代码里不出现任何平台名词**（QQ / 群号 / telnet / SnowLuma / OneBot）
- 场景描述由 adapter 提供，核心只负责拼装
- 判断依据：`core/` 里 `grep QQ` 应当只在注释里解释分层，不能出现在提示词或逻辑里

## 二、"像人"是核心能力，不是通道特性

这些行为属于**核心**，所有通道自动继承：

- 发言节奏（多条气泡之间的停顿、按字数计时、抖动）——`core/pacing.py`
- 该不该开口（门控：@、频率、连发合并、每小时上限）——`core/pipeline/`
- 说话的分寸与人格（人格卡由插件提供，机制在核心）——`core/context.py`
- 记忆：她是谁（self）/ 这一处的记忆（scope）/ 刚聊了什么（turn）
- 想说什么、说几条、什么时候收口（工具循环）——`core/agent.py`

反过来，**任何"只对某个软件有意义"的东西都不许进核心**：输入状态、戳一戳、引用回复的字段名、群文件上传……

## 三、三种接口，穷尽扩展方式

| 想加什么 | 实现什么接口 | 放哪儿 |
|---|---|---|
| 接入新的聊天软件 | `Channel`（`start/send/abilities/supports/describe`） | `adapters/<名字>/` |
| 给模型新的能力 | `ToolSpec`（名字/描述/参数/requires） | `plugins/<名字>/` 或核心内置 |
| 让她知道更多东西 | `ContextProvider`（`contribute` / `on_message` / `on_reply`） | `plugins/<名字>/` |

除此之外不新增扩展点。

## 四、失败要响亮

- 配置错（key 读不到、端口被占）→ **启动失败**并留 ERROR 日志，不要静默不说话
- 插件崩了 → 记日志、重启、连续失败 3 次熔断，不让它拖垮核心
- 宁可"她没说话但你从日志里知道为什么"，也不要"看起来在跑其实什么也没做"

## 五、缓存友好：稳定在前，变动在后

提示词顺序固定：人格+规则 → self 记忆 → scope 记忆 → 场景 → 最近 → 当前。
前缀稳定，DeepSeek 前缀缓存才能命中（实测 70~96%）。改顺序 = 直接涨钱。

## 六、记忆分三层，写入频率不同

| 层 | 内容 | 谁写 | 频率 |
|---|---|---|---|
| self | 她是谁、关于主人的事、经验教训 | 主人明确要求 / 每日自省 | 极低 |
| scope | 群印象、成员档案、规矩 | 后台学习任务 | 每小时 |
| turn | 最近 20 条 | 自动 | 每条消息 |

混在一起会被某个群的闲聊污染，变成"只记得最后说话那个人"的复读机。

## 六点五、接入新通道：先摸清接口，再动手

新接一个平台（QQ、Discord、Telegram…），**第一步不是写 adapter，而是把这个平台支持的
所有接口列成文档**（`docs/<通道名>_API.md`）：动作名 / 用途 / 风险 / 我们用了没。

理由：不先摸清，就会在 adapter 里自己造一层"通用抽象"去兼容想象中的差异——
那层多余的东西以后每个平台都要维护一遍，而且大概率是错的。

清单有了之后：
1. 把接口按 transport / query / control 分三类
2. transport 映射到**封闭动词表**（text/at/quote/image/file/face/poke/voice），不发明新动词
3. control 类（踢人、禁言、退群）默认不做，要做先有权限模型
4. 写 `describe` / `scope_info` / `profile` / `start` / `send` 五个东西就够
5. 能力先标 `experimental`，真机验证后再 `ready`

详细清单见 `docs/CHANNEL_ONBOARDING.md`。

**行内占位符属于核心协议**：像"文字里夹一个平台自带表情"这种写法（`[表情:名字]`），
必须定义在 `core/capability.py` 一处，核心负责生成与教模型，adapter 只负责翻译。
adapter 里自己拼这类字符串 = 边界被侵蚀（有守卫测试会拦）。

## 七、开发与部署分离

- 仓库里**不放任何服务器地址、密钥路径、个人数据**
- 部署脚本必须显式传目标（`DEEPSEA_HOST` / `DEEPSEA_KEY`）
- 配置分环境：`core.example.toml`（模板）/ `core.toml`（本机，不进 git）

## 八、通道能力：诚实失败，不静默降级

核心**不做"万能翻译"**（把"发文件"翻译成某种通用表述）。原因：词汇会无限膨胀、
只能取最低公分母、插件行为不可预测。

替代方案，三件事：

1. **能力声明**：通道声明 `abilities`，工具/插件声明 `requires`，核心据此过滤
2. **诚实失败**：通道做不到就报错 `这个通道做不到「file」`，绝不偷偷换成文字
3. **插件给意图**：插件返回 `{"send": [{"kind": "file", ...}]}`，核心负责执行与能力检查；
   降级由**插件或模型**决定，不是核心偷偷决定

动词表是**封闭的**（text/at/quote/image/file/face/poke/voice）：加动词要改核心（少见），
实现动词只改 adapter（常见）。这样核心不会因为"支持更多通道"而膨胀。

**通道能力 ≠ 她掌握的能力**（两个概念，提示词里必须分开说）：

| | 含义 | 来源 |
|---|---|---|
| **通道能力**（abilities） | 这个通道**送得出去什么**：文字/图片/文件/表情/@ | adapter 声明 |
| **掌握能力**（skills） | 她**实际会做什么**：只取决于给她的工具 | 工具清单 |

"能发图片"只是能把**现成的**图送出去，不等于会画图；"能发文件"不等于会写文件。
提示词里绝不能用"你能做的动作"来描述通道能力——踩过两次：
终端里答"能发文件"、群里答"会画图"。

**能力必须让模型知道**：每轮把两者分别写进提示词，并明确"以工具为准"。
只过滤工具是不够的——**看不见工具 ≠ 知道自己不会**。

工具还要再分三类，**只有"对外动作"才算能力**：

| kind | 例子 | 进不进能力清单 |
|---|---|---|
| `action` | 说话、发表情、发文件 | ✅ 这才是"她会做什么" |
| `query` | 查表情名 | 单独一行"另外还能查" |
| `control` | decide（判断接不接）、finish（收工） | ❌ 内部流程，不是能力 |

工具还有 **status**：`ready` 才给模型；`experimental`（写了但没真机验证）和 `planned` 一律不出现。
踩过的坑：`send_file` / `send_image` 代码写了但没验证，一度出现在清单里，于是她在群里承诺
"能发文件、能画图"——**没验证过的能力就是没有的能力**。
